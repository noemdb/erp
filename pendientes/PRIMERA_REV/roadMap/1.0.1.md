## Roadmap seguro — ERP Tributario Venezolano

### Principio rector

**Norma → interpretación aprobada → regla versionada → escenario dorado → implementación → pruebas → evidencia → producción.**

Nunca:

**interpretación → código → "después validamos".**

---

# F0 — Cierre fiscal y funcional

**Objetivo:** conseguir una base fiscal aprobada antes de declarar operativo el motor.

### F0.1 — Matriz de Reglas v1

Cerrar y aprobar:

* IVA:

  * condición de agente;
  * exclusiones;
  * 75 %;
  * 100 %;
  * momento de retención;
  * comprobantes;
  * numeración;
  * vigencias.
* ISLR:

  * conceptos realmente utilizados;
  * beneficiarios;
  * residencia;
  * base;
  * porcentaje;
  * mínimo;
  * UT;
  * sustraendo;
  * momento de retención;
  * vigencias.

**Gate F0.1:**

> Cada regla tiene fuente, artículo, vigencia, condiciones, fórmula y ejemplo aprobado.

No aprobado → **no entra al motor productivo**.

---

### F0.2 — Decisiones G1–G12

Resolver formalmente:

| Decisión | Cierre requerido                                             |
| -------- | ------------------------------------------------------------ |
| G1       | Período IVA por empresa + condición fiscal                   |
| G2       | Pago/abono + fecha + importe + parciales + base + sustraendo |
| G4       | Fecha/tipo de cambio BCV + diferencias cambiarias            |
| G7       | Facturas/Z + sucursal + prevención de duplicados             |
| G8       | Definición matemática de 8 decimales                         |
| G9       | Numeración IVA/ISLR + reinicio                               |
| G11      | Métodos de pago                                              |
| G12      | Calendario fiscal                                            |
| Roles    | Preparar/revisar/aprobar/emitir/anular/reemitir              |

**Gate F0.2:**

> Cada decisión tiene responsable, respuesta, evidencia y fecha.

---

### F0.3 — Muestras reales

Obtener:

* XLSX original;
* ≥ 1 mes de CSV del legacy;
* ≥ 1 mes de archivos Z;
* comprobantes reales IVA;
* comprobantes reales ISLR;
* ejemplos de pagos/abonos;
* documentos de empresas piloto.

Anonimizar antes de utilizarlos como datos de prueba.

**Gate F0.3:**

> Las muestras representan realmente los formatos que el ERP deberá procesar.

---

# F1 — Modelo fiscal y datos maestros

Con F0 cerrado, construir la **fuente estructural de verdad**.

### Empresas

* RIF;
* condición fiscal;
* condición de agente;
* período IVA;
* sucursales;
* vigencia del perfil.

### Terceros

* RIF;
* persona natural/jurídica;
* residente/no residente;
* historial fiscal.

### Catálogos

* conceptos ISLR;
* reglas IVA;
* reglas ISLR;
* tasas;
* tipos de cambio;
* métodos de pago;
* series documentales;
* calendarios.

### Regla crítica

Todo dato fiscal susceptible de cambiar debe ser **versionable**.

No sobrescribir:

> regla anterior → regla nueva

sino:

> regla v1 → vigencia → regla v2 → nueva vigencia.

# F2 — Motor tributario

Aquí entra el cálculo propiamente dicho.

Debe ser un motor **determinista y puro**:

```text
Entrada
   ↓
Contexto fiscal
   ↓
Regla vigente
   ↓
Cálculo
   ↓
Resultado
   ↓
Explicación
```

Cada cálculo debe conservar:

* regla aplicada;
* versión;
* vigencia;
* parámetros;
* base;
* porcentaje;
* sustraendo;
* resultado;
* explicación.

### F2.1 IVA

Implementar únicamente reglas aprobadas.

### F2.2 ISLR

Implementar por:

```text
concepto
+ beneficiario
+ condición
+ vigencia
+ base
+ porcentaje
+ sustraendo
```

### F2.3 G2

Integrar finalmente:

```text
pago
        o
abono en cuenta
        ↓
evento fiscal
        ↓
base atribuible
        ↓
retención
```

**Gate F2:**

> 100 % de escenarios dorados aprobados pasan.

Si falla un golden:

**F2 permanece bloqueada.**

# F5 — Retenciones

Implementar el ciclo completo:

```text
Borrador
   ↓
Cálculo
   ↓
Previsualización
   ↓
Revisión
   ↓
Aprobación
   ↓
Emisión
   ↓
Entrega
```

Y excepciones:

```text
Anulación
   ↓
Sustitución / reemisión
```

### Numeración

Nunca reutilizar un número emitido.

Nunca hacer:

```sql
MAX(numero) + 1
```

La documentación existente ya establece esta invariante de numeración. 

---

# F6 — Períodos fiscales

Implementar formalmente:

```text
OPEN
  ↓
UNDER_REVIEW
  ↓
CLOSED
```

y únicamente mediante procedimiento autorizado:

```text
CLOSED
  ↓
REOPENED
  ↓
UNDER_REVIEW
  ↓
CLOSED
```

Cada reapertura requiere:

* usuario;
* fecha;
* motivo;
* auditoría.

No permitir operaciones incompatibles con un período cerrado.

La documentación ya contempla esta máquina de estados y `closure_hash`.

# F12 — Piloto controlado

No hacer inmediatamente un go-live completo.

Seleccionar:

* 1–3 empresas;
* períodos definidos;
* usuarios definidos;
* volumen controlado.

Ejecutar:

```text
Legacy
   ↓
ERP nuevo
   ↓
Comparación
   ↓
Diferencias
   ↓
Explicación
   ↓
Corrección
```

No corregir diferencias simplemente cambiando el resultado esperado.

Primero determinar:

> ¿el legacy está correcto?, ¿la regla aprobada está correcta?, ¿la importación está correcta?, ¿o el motor está incorrecto?

# Gate de seguridad transversal

Yo agregaría un mecanismo que atraviese **todas las fases**:

## Fiscal Change Control

Cada modificación tributaria debe generar:

```text
Cambio normativo
       ↓
Identificación de fuente
       ↓
Análisis de impacto
       ↓
Nueva versión de regla
       ↓
Nuevos escenarios
       ↓
Regresión completa
       ↓
Aprobación contador
       ↓
Fecha de vigencia
       ↓
Activación
```

Y conservar la regla histórica.

Ejemplo conceptual:

```text
IVA-01 v1
vigente: 01/08/2025 → 31/12/2026

IVA-01 v2
vigente: 01/01/2027 → ...
```

**Nunca:**

```text
UPDATE IVA-01
SET porcentaje = nuevo_valor
```

si eso destruye la capacidad de reproducir un cálculo histórico.

La arquitectura existente ya establece precisamente la conservación de `rule_version_id` y del snapshot de parámetros. 

---

# Los 7 bloqueos que no permitiría saltar

1. **Regla fiscal sin fuente/vigencia → BLOQUEADO.**
2. **Regla sin aprobación del contador → BLOQUEADO.**
3. **Escenario dorado sin aprobación → no es golden.**
4. **Cálculo ambiguo → no emitir.**
5. **Documento real sin trazabilidad → no importar definitivamente.**
6. **Período cerrado → no modificar silenciosamente.**
7. **Cambio normativo → nueva versión, nunca sobrescritura histórica.**

### La regla de oro del proyecto

**F0 no es documentación administrativa. Es el firewall del sistema tributario.**

Mientras F0 esté abierta, podemos desarrollar infraestructura, UI, importadores, staging, autenticación, auditoría y componentes no dependientes de una decisión fiscal. Pero **no debemos cerrar como "correcto" un cálculo tributario cuya regla, vigencia o interpretación aún esté pendiente de aprobación**.

Esto es especialmente importante en **G2, ISLR, G7, G8 y G9**, porque son precisamente los puntos donde una implementación técnicamente correcta puede producir un resultado fiscal incorrecto si la decisión de negocio/contabilidad todavía no está cerrada.
