## 3. Reportes y comprobantes

Esta fase debe cerrar el **contrato de salida fiscal** del sistema. El XLSX suministrado no debe tratarse simplemente como una plantilla visual: en el proyecto está definido como **golden master**, es decir, una salida de referencia del cliente/contador contra la cual se compara el sistema. 

Además, el diseño actual ya establece que los reportes se generan desde los documentos fuente, se versionan y almacenan con `data_snapshot` y `sha256`; por tanto, esta fase debe validar que esa arquitectura realmente produzca salidas fieles y reproducibles. 

# 3. Reportes y comprobantes

## Objetivo de la fase

Demostrar que el ERP puede generar los libros, resúmenes y comprobantes aprobados por el cliente con:

* fidelidad estructural al formato aprobado;
* exactitud de datos;
* exactitud de cálculos;
* trazabilidad hasta los documentos fuente;
* conciliación entre reportes;
* reproducibilidad después del cierre;
* conservación de la evidencia emitida.

El criterio no debe ser simplemente:

> “El Excel abre y el PDF se ve bien”.

El criterio debe ser:

> **La misma información fiscal produce la misma salida, puede explicarse hasta su origen y permanece reproducible después del cierre.**

---

# 3.1 Ejecutar spike de PDF/Excel fiel

## Objetivo

Validar técnicamente que el sistema puede producir los formatos aprobados sin reconstruirlos manualmente en cada generación.

La arquitectura ya establece:

* **Excel:** `exceljs` rellenando la plantilla original.
* **PDF:** HTML/CSS → PDF server-side mediante Playwright/Chromium.
* almacenamiento privado de los archivos generados;
* `sha256` para integridad. 

El spike debe comprobar estas decisiones con el archivo real.

## Excel

El flujo debe ser:

```text
XLSX aprobado
      ↓
Identificación de hojas
      ↓
Identificación de celdas
      ↓
Identificación de fórmulas
      ↓
Identificación de formatos
      ↓
Mapeo dato fiscal → celda
      ↓
Generación con datos del ERP
      ↓
Comparación
```

No conviene crear un Excel completamente nuevo si la plantilla aprobada puede utilizarse como base.

### Debe comprobarse

* nombre de hojas;
* orden de hojas;
* ancho de columnas;
* alto de filas;
* celdas combinadas;
* bordes;
* formatos numéricos;
* fechas;
* porcentajes;
* fórmulas;
* encabezados;
* pies de página;
* impresión;
* orientación;
* saltos de página;
* áreas de impresión;
* congelación de paneles;
* textos legales;
* totales;
* subtotales.

### Punto crítico

Debe diferenciarse:

```text
valor generado
```

de:

```text
fórmula existente en plantilla
```

No sustituir una fórmula por un valor calculado desde JavaScript si el formato aprobado exige conservar la fórmula.

Asimismo, debe documentarse cuáles fórmulas son solamente de presentación y cuáles representan cálculos fiscales.

# 3.3 Comparación Excel celda a celda

Este debe ser un **gate formal**, no una revisión visual informal.

## Crear una referencia

Primero se valida el XLSX entregado por el cliente:

```text
XLSX original
      ↓
Revisión contador
      ↓
Anonimización
      ↓
Golden Master
      ↓
SHA-256
      ↓
Registro de versión
```

La documentación actual indica que el XLSX disponible todavía está pendiente de validación como golden master y que sus datos identificables no deben copiarse directamente a fixtures o documentación. 

## Comparación

La prueba debe producir algo similar a:

```text
Hoja: Libro de Compras

Celda     Golden Master       ERP             Resultado
---------------------------------------------------------
A1        LIBRO DE COMPRAS    LIBRO DE COMPRAS  OK
B4        2026-09-01          2026-09-01        OK
F8        120.00              120.00            OK
G8        19.20               19.20             OK
H8        14.40               14.40             OK
...
```

Pero además de comparar valores debe distinguir:

### Nivel 1 — estructura

```text
hojas
rangos
merged cells
filas
columnas
```

### Nivel 2 — presentación

```text
font
border
alignment
number format
fill
width
height
print settings
```

### Nivel 3 — contenido

```text
texto
fecha
número
fórmula
boolean
```

### Nivel 4 — semántica

```text
total del libro
IVA
retenciones
bases
cantidad de operaciones
```

No toda diferencia de Excel debe considerarse error fiscal.

Por ejemplo:

```text
metadata interna diferente → posiblemente irrelevante
fórmula diferente → requiere revisión
monto diferente → error
RIF diferente → error
total diferente → error
formato monetario diferente → revisar
```

Por ello el comparador debe clasificar las diferencias.

# 3.4 Regresión visual de PDF

Para cada reporte aprobado debe existir un snapshot de referencia.

Ejemplo:

```text
golden/
  purchase-book/
    v1/page-001.png
    v1/page-002.png

  sales-book/
    v1/page-001.png

  iva-summary/
    v1/page-001.png

  iva-withholding/
    v1/page-001.png

  islr-withholding/
    v1/page-001.png
```

Una nueva generación se compara contra el snapshot.

## Tipos de resultado

```text
MATCH
EXPECTED_CHANGE
UNEXPECTED_CHANGE
```

Esto es importante porque una modificación legítima del formato no debe romper indefinidamente las pruebas.

Si el contador aprueba una nueva versión:

```text
Golden v1
    ↓
cambio aprobado
    ↓
Golden v2
```

Nunca reemplazar silenciosamente el snapshot anterior.

# 3.5 Validar totales, cortes y conciliación con período real

Este es probablemente el gate más importante de la sección.

El sistema ya contempla:

```text
Libro de Compras
Libro de Ventas
Resumen IVA
Retenciones
Conciliación
```

y una tolerancia de conciliación actualmente definida en el diseño como `0`, salvo que ADR-014 establezca posteriormente una tolerancia aprobada. 

## Usar un período real

No cerrar esta fase con datos sintéticos únicamente.

Debe seleccionarse:

```text
Empresa real anonimizada
+
Período real
+
Compras
+
Ventas
+
NC/ND
+
Retenciones
+
Z si aplica
+
Resumen existente
```

y comparar:

```text
Legacy / Excel
       ↕
      ERP
```

## Conciliación mínima

### Libro de Compras

```text
Número de documentos
Base imponible
IVA causado
Exentos/no sujetos
IVA retenido
Totales
```

### Libro de Ventas

```text
Número de documentos
Ventas gravadas
Ventas exentas/no sujetas
Base imponible
IVA causado
Notas de crédito
Notas de débito
Retenciones
Z
Totales
```

### Resumen IVA

Debe comprobarse que:

```text
Libro Compras
      ↓
Crédito fiscal
      ↓
Resumen
```

y:

```text
Libro Ventas
      ↓
Débito fiscal
      ↓
Resumen
```

además de:

```text
Retenciones
      ↓
Resumen IVA
```

produzcan los valores esperados.

# 3.6 Conciliación con trazabilidad

Un total no debe limitarse a mostrar:

```text
Crédito fiscal: Bs. X
```

Debe permitir:

```text
Crédito fiscal
      ↓
Documentos que lo componen
      ↓
Factura
      ↓
Línea
      ↓
Base
      ↓
IVA
      ↓
Regla aplicada
```

La métrica del proyecto establece precisamente como objetivo que ante la pregunta:

> “¿De dónde salió?”

la respuesta pueda obtenerse en ≤3 clics. 

Esto debe convertirse en criterio de aceptación de F5.

# 3.7 Cortes por período

Debe probarse explícitamente que una operación no cambia de período solamente porque fue registrada posteriormente.

Ejemplo:

```text
Fecha fiscal: agosto
Registro en ERP: septiembre
```

Resultado esperado:

```text
Período fiscal → agosto
```

La documentación establece expresamente que la `fecha_fiscal` determina el período y que la fecha de registro no la sustituye. 

También deben probarse:

* documento de período anterior registrado tarde;
* documento posterior;
* NC de período anterior;
* retención de período anterior;
* operación registrada después del cierre;
* reapertura;
* ajuste post-cierre, si corresponde.

# 3.8 Comprobantes: ciclo completo

Los comprobantes no deben probarse únicamente como archivos PDF.

El ciclo completo debe ser:

```text
Cálculo
  ↓
Preview
  ↓
Aprobación
  ↓
Numeración
  ↓
Emisión
  ↓
PDF/Excel
  ↓
Hash
  ↓
Entrega
  ↓
Auditoría
```

El diseño actual establece que una emisión debe realizarse dentro de una transacción, conservar snapshot completo y regla aplicada, generar el archivo, calcular `sha256` y registrar el evento de auditoría. 

Debe probarse además:

```text
emitir
↓
anular
↓
sustituir
```

sin reutilizar el número original.

# 3.9 Reproducibilidad de reportes cerrados

## Objetivo

Demostrar que un reporte correspondiente a un período cerrado puede regenerarse posteriormente sin cambiar su contenido fiscal.

El modelo actual define:

```text
generated_reports
 ├── kind
 ├── version
 ├── data_snapshot
 ├── sha256
 └── storage_path
```

y el cierre conserva un `closure_hash`. 

## Prueba de reproducibilidad

Procedimiento:

```text
1. Abrir período
2. Cargar datos
3. Generar reporte
4. Guardar snapshot
5. Calcular SHA-256
6. Cerrar período
7. Regenerar reporte
8. Comparar contenido
9. Comparar hash
```

Resultado esperado:

```text
SHA original = SHA regenerado
```

o, si el formato contiene metadata inevitablemente variable, debe definirse una representación canónica para comparar el **contenido fiscal**, sin depender de timestamps o metadata de archivo.

### Importante

No asumir que dos archivos binarios idénticos visualmente tendrán necesariamente el mismo hash si el generador introduce metadata variable.

Por eso hay que distinguir:

```text
reproducibilidad fiscal
```

de:

```text
identidad binaria del archivo
```

La primera es obligatoria; la segunda debe conseguirse si la herramienta y el formato lo permiten.

# 3.12 Criterios de aceptación

La sección queda cerrada únicamente cuando:

* [ ] XLSX del cliente fue validado y declarado **Golden Master**.
* [ ] Datos identificables fueron anonimizados para fixtures.
* [ ] Cada hoja requerida tiene mapeo documentado.
* [ ] Excel generado pasa comparación estructural.
* [ ] Excel generado pasa comparación de valores.
* [ ] Diferencias de fórmulas están justificadas.
* [ ] PDF pasa regresión visual.
* [ ] Los comprobantes IVA pasan pruebas de una y múltiples facturas.
* [ ] Los comprobantes ISLR pasan las pruebas correspondientes a conceptos aprobados.
* [ ] Existe al menos un período real procesado.
* [ ] Libros y resumen concilian.
* [ ] Z concilia cuando la empresa utiliza modo Z.
* [ ] Los cortes fiscales son correctos.
* [ ] Existe drill-down desde totales hasta documentos.
* [ ] Un período cerrado bloquea modificaciones.
* [ ] Un reporte cerrado puede regenerarse de forma reproducible.
* [ ] Existe evidencia de cada prueba.
* [ ] El contador valida las diferencias que no sean puramente técnicas.

# Gate F5 — Reportes y comprobantes

El gate debe expresarse como:

```text
             DATOS REALES
                  │
                  ▼
          DOCUMENTOS FUENTE
                  │
                  ▼
          MOTOR TRIBUTARIO
                  │
                  ▼
       ┌──────────┴──────────┐
       ▼                     ▼
   LIBROS                  RETENCIONES
       │                     │
       └──────────┬──────────┘
                  ▼
             RESUMEN IVA
                  │
                  ▼
            CONCILIACIÓN
                  │
                  ▼
        PDF / XLSX / CSV
                  │
                  ▼
       GOLDEN + SNAPSHOTS
                  │
                  ▼
          CIERRE FISCAL
                  │
                  ▼
          REPRODUCIBILIDAD
```

## Estado de bloqueo

Esta fase **no debe declararse cerrada** si:

1. el XLSX aún no está validado como Golden Master;
2. no existe un período real;
3. no se ha ejecutado la comparación celda a celda;
4. no se ha ejecutado la regresión visual de PDF;
5. existe alguna diferencia fiscal no explicada;
6. un reporte cerrado cambia al regenerarse;
7. no puede trazarse un total hasta sus documentos fuente.

La documentación actual refleja precisamente que el spike de PDF/Excel fiel todavía está pendiente y que requiere el XLSX golden del cliente. 

## Resultado esperado de F5

Al terminar esta fase, debe poder hacerse una demostración completa:

```text
Período real
     ↓
Importación / documentos
     ↓
Libro de Compras
     ↓
Libro de Ventas
     ↓
Retenciones
     ↓
Resumen IVA
     ↓
Conciliación
     ↓
Excel aprobado
     ↓
PDF aprobado
     ↓
Cierre
     ↓
Regeneración
     ↓
MISMA INFORMACIÓN FISCAL
```

Ese es el punto en el que el ERP deja de ser solamente un sistema que **calcula** y pasa a demostrar que puede **producir la documentación fiscal operativa de forma controlada y reproducible**.

Un detalle importante para el siguiente paso: el propio proyecto fija **M2 = “mes real = Excel”**, **M4 = cierre reproducible** y **M5 = paralelo Excel vs. sistema = 0** como métricas de éxito. Por tanto, estas cuatro tareas de F5 no son una validación estética final; son parte de los criterios centrales de aceptación del producto.
