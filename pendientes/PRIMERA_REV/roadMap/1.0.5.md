## 5. F7 — Operación y go-live

### Objetivo

Cerrar la transición desde el entorno de desarrollo/pruebas hacia una **operación fiscal real, controlada y recuperable**, asegurando simultáneamente:

* integridad de los datos históricos;
* mínimo privilegio en infraestructura y base de datos;
* capacidad real de recuperación ante pérdida o corrupción;
* seguridad operacional;
* usuarios capacitados;
* procedimientos documentados;
* aceptación formal del contador y del responsable del cliente.

La documentación actual identifica F7 como la fase de **Hardening y operación**, con healthcheck, logs y runbooks ya implementados, mientras que **migración histórica, paralelo Excel/sistema, UAT y go-live continúan pendientes y requieren contador y muestras reales**. 

> **Regla:** tener el software funcionando no equivale a estar listo para producción. El go-live requiere evidencia técnica, operativa y fiscal.

---

### 5.1 Migración histórica y conciliación contra Excel

#### Objetivo

Migrar el período histórico aprobado por el cliente sin perder:

* documentos;
* fechas fiscales;
* terceros;
* RIF;
* bases;
* IVA;
* retenciones;
* pagos;
* relaciones entre documentos;
* período fiscal;
* trazabilidad del origen.

La migración debe ser **reproducible e idempotente** y debe poder demostrar de dónde proviene cada dato.

La arquitectura ya define el pipeline:

```text
Archivo original
      ↓
source_files
      ↓
import_batches
      ↓
import_rows
      ↓
validación
      ↓
confirmación
      ↓
documentos definitivos
```

con conservación del archivo original, `sha256`, fila de origen y trazabilidad. 

#### Procedimiento

**1. Definir alcance histórico**

El cliente debe aprobar:

```text
Empresa(s)
Período(s)
Fuente(s)
Fecha de corte
Documentos incluidos
Documentos excluidos
```

No debe migrarse “todo el histórico” por defecto.

**2. Preservar los originales**

Cada archivo debe conservar:

```text
nombre original
tipo
fecha de recepción
sha256
empresa
período
origen
usuario que importó
```

El archivo original debe permanecer inalterado.

**3. Ejecutar migración en staging**

Primero:

```text
CSV/XLSX/Z
   ↓
staging
   ↓
validación
   ↓
errores / advertencias
   ↓
corrección
   ↓
confirmación
```

Nunca importar directamente sobre las tablas fiscales definitivas sin pasar por staging.

**4. Conciliar**

Para cada período:

```text
Excel histórico
      ↕
ERP
```

comparando como mínimo:

| Control                | Resultado esperado |
| ---------------------- | -----------------: |
| Cantidad de documentos |              Igual |
| Base imponible         |              Igual |
| IVA                    |              Igual |
| Retenciones            |              Igual |
| Totales por período    |              Igual |
| Terceros               |        Conciliados |
| Fechas fiscales        |        Conciliadas |
| NC/ND                  |        Conciliadas |
| Sucursales             |        Conciliadas |
| Z, cuando aplique      |         Conciliado |

#### Política de diferencias

Toda diferencia debe terminar en uno de estos estados:

```text
CORREGIR
JUSTIFICAR
APROBAR
```

Nunca:

```text
IGNORAR
```

Una diferencia fiscal no aprobada mantiene bloqueado el go-live.

#### Evidencia

Por cada migración:

```text
migration-report/
├── source-files.csv
├── row-counts.csv
├── totals-by-period.csv
├── reconciliation.xlsx
├── differences.csv
└── migration-report.md
```

### Criterio de aceptación

```text
Documentos migrados:              100 %
Documentos rechazados:             0 sin tratamiento
Diferencias fiscales pendientes:  0
Archivos originales preservados:  100 %
Trazabilidad de origen:            100 %
Conciliación aprobada:             100 %
```

## 5.2 Rol de base de datos de mínimo privilegio

### Objetivo

La aplicación no debe conectarse a PostgreSQL utilizando un usuario con privilegios administrativos innecesarios.

Debe existir separación entre:

```text
administración/migraciones
             │
             └── usuario administrativo

aplicación
             │
             └── usuario runtime de mínimo privilegio
```

La aplicación debe tener únicamente las capacidades necesarias para ejecutar las operaciones normales del ERP.

### Validaciones

Comprobar explícitamente que el usuario runtime **no pueda**:

* crear/eliminar bases;
* crear/eliminar roles;
* modificar permisos;
* alterar extensiones;
* modificar esquema fuera de las operaciones previstas;
* acceder a otras bases;
* leer secretos almacenados fuera de su ámbito;
* ejecutar operaciones administrativas.

Y que sí pueda realizar:

* `SELECT`;
* `INSERT`;
* `UPDATE`;
* las operaciones estrictamente necesarias para la aplicación;
* ejecución de funciones/procedimientos específicamente autorizados, si existen.

### Prueba negativa

No basta con revisar el SQL de configuración.

Debe intentarse realmente:

```text
CREATE ROLE
DROP TABLE
ALTER TABLE
CREATE EXTENSION
DROP DATABASE
GRANT
REVOKE
```

y comprobar que el usuario de aplicación sea rechazado.

### Separación de credenciales

Las credenciales de:

```text
migración
desarrollo
staging
producción
```

no deben ser intercambiables.

Especialmente, las credenciales administrativas no deben estar disponibles para el proceso normal de Next.js/worker.

### Criterio de aceptación

```text
Usuario runtime identificado:       ✓
Privilegios mínimos verificados:    ✓
Operaciones administrativas:        0 permitidas
Acceso fuera del ámbito:            0
Credenciales admin en runtime:      0
Prueba negativa ejecutada:           ✓
```

## 5.3 Backups cifrados y Restore Drill

### Objetivo

No considerar el backup como garantía hasta demostrar que **puede restaurarse**.

La documentación establece:

* `pg_dump` diario;
* WAL/PITR;
* copia fuera del servidor;
* cifrado;
* restore drill periódico;
* objetivo RPO ≤ 24 h, idealmente ≤ 1 h;
* RTO pendiente de definición con el cliente. 

El runbook existente contempla restauración mediante Neon/PITR o `pg_dump`/`pg_restore` y exige registrar fecha, responsable, RPO medido y observaciones. 

### Arquitectura mínima

```text
                 PRODUCCIÓN
                     │
              PostgreSQL / Neon
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       PITR/WAL              pg_dump
          │                     │
          └──────────┬──────────┘
                     ↓
             almacenamiento
                externo
                     │
                  cifrado
```

El backup no debe depender exclusivamente del mismo servidor cuya pérdida se pretende cubrir.

### Prueba de restauración

Ejecutar un drill real:

1. Seleccionar un punto de recuperación.
2. Restaurar a un entorno aislado.
3. Verificar estructura.
4. Verificar datos.
5. Verificar períodos cerrados.
6. Verificar `closure_hash`.
7. Verificar `generated_reports`.
8. Ejecutar `/api/health`.
9. Ejecutar pruebas mínimas de lectura.
10. Registrar RPO.
11. Medir tiempo total de recuperación.
12. Documentar cualquier diferencia.

El runbook establece específicamente comprobar `closure_hash` y `generated_reports` después del restore. 

### No basta con verificar que PostgreSQL inicia

El restore debe demostrar:

```text
Base restaurada
      ↓
Datos íntegros
      ↓
Períodos íntegros
      ↓
Auditoría íntegra
      ↓
Reportes reproducibles
      ↓
Aplicación operativa
```

### Criterio de aceptación

```text
Backup automático:             ✓
Backup externo:                ✓
Backup cifrado:                ✓
PITR/WAL verificado:           ✓
Restore drill ejecutado:       ✓
Restore exitoso:                ✓
RPO medido:                    ✓
RTO medido:                    ✓
Evidencia documentada:         ✓
```

**Bloqueador:** un backup que nunca ha sido restaurado exitosamente no debe considerarse evidencia suficiente de recuperabilidad.

# 5.5 UAT por rol

### Objetivo

El **User Acceptance Testing** debe demostrar que los usuarios reales pueden ejecutar sus responsabilidades con datos representativos.

No sustituye las pruebas automatizadas de la fase 4.

La diferencia es:

```text
Fase 4 → ¿el sistema funciona correctamente?
F7      → ¿el usuario puede operar correctamente el sistema?
```

### UAT Administrativo

Debe completar:

```text
login
→ seleccionar empresa
→ importar
→ revisar errores
→ corregir
→ confirmar
→ consultar documentos
→ descargar reporte
```

### UAT Contador

Debe completar:

```text
login
→ revisar período
→ validar datos
→ revisar cálculos
→ revisar explicación
→ emitir
→ consultar comprobante
→ conciliar
→ cerrar período
→ descargar reportes
```

Debe además verificar que el sistema bloquee correctamente las situaciones fiscales pendientes.

### UAT Auditor

Debe completar:

```text
login
→ consultar empresa autorizada
→ consultar período
→ drill-down
→ documento origen
→ regla aplicada
→ comprobante
→ auditoría
→ reporte
```

### UAT Administrador del sistema

Debe verificar:

```text
usuarios
empresas
roles
permisos
sesiones
logs
health
```

### Evidencia

Cada UAT debe producir:

```text
rol
usuario
empresa
fecha
versión
casos ejecutados
resultado
incidencias
firma/aprobación
```

# 5.8 Firma de aceptación y autorización de go-live

La firma debe ser el **último gate**, no una formalidad posterior al despliegue.

El documento debe identificar:

```text
Proyecto
Empresa(s)
Período(s) evaluados
Versión del sistema
Versión de reglas
Fecha de evaluación
Resultado UAT
Resultado de conciliación
Incidencias abiertas
Excepciones aprobadas
```

Y contener dos aprobaciones diferenciadas:

### Contador responsable

Confirma que:

* las reglas fiscales utilizadas fueron revisadas;
* los escenarios aprobados fueron satisfactorios;
* el período de prueba fue conciliado;
* las diferencias fiscales pendientes están en cero o formalmente aprobadas;
* los comprobantes/reportes son aceptables para la operación definida.

### Responsable del cliente

Confirma que:

* los usuarios fueron capacitados;
* los roles y empresas están correctamente configurados;
* los datos migrados fueron recibidos;
* los procedimientos operativos fueron entregados;
* el cliente acepta iniciar operación bajo el alcance definido.

# 5.9 Gate definitivo de F7

F7 puede marcarse como **ACEPTADA / GO-LIVE AUTORIZADO** únicamente cuando:

| Área             | Criterio                              |
| ---------------- | ------------------------------------- |
| Migración        | Histórica completada y conciliada     |
| Excel vs sistema | Sin diferencias fiscales no aprobadas |
| Base de datos    | Mínimo privilegio verificado          |
| Backups          | Externos, cifrados y funcionando      |
| Restore          | Drill exitoso y documentado           |
| Seguridad        | Hardening completado                  |
| UAT              | Todos los roles críticos aprobados    |
| Capacitación     | Usuarios objetivo capacitados         |
| Manuales         | Entregados y disponibles              |
| Runbooks         | Probados, no solo redactados          |
| Fiscal           | Contador valida el resultado          |
| Cliente          | Responsable acepta operación          |
| Go-live          | Checklist firmado                     |

### Regla de bloqueo final

El sistema **no debe pasar a producción fiscal** si falta cualquiera de estos elementos:

```text
Matriz fiscal firmada
        +
Escenarios dorados aprobados
        +
Período conciliado
        +
Seguridad aceptada
        +
Backup probado
        +
Restore probado
        +
UAT aprobado
        +
Capacitación
        +
Firma contador
        +
Firma responsable cliente
```

Esto es especialmente importante en el estado actual del proyecto: la propia documentación mantiene **F0/F2 y varios puntos fiscales como bloqueados o pendientes**, y F7 indica expresamente que migración histórica, paralelo Excel/sistema, UAT y go-live requieren contador y muestras reales.

### Resultado final de F7

El resultado que debe quedar documentado no es simplemente **“producción desplegada”**, sino:

> **“Versión X del ERP Tributario, con reglas y escenarios fiscales aprobados, datos históricos conciliados, controles de seguridad verificados, recuperación ante desastre probada, usuarios capacitados y aceptación formal del contador y del responsable del cliente, queda autorizada para iniciar operación bajo el alcance y período definidos.”**

Con esto, **F0–F7 forman un circuito completo de entrada a producción**:

```text
F0  Línea base fiscal
 ↓
F1  Fundaciones
 ↓
F2  Motor tributario
 ↓
F3  Importación
 ↓
F4  Retenciones
 ↓
F5  Libros / reportes / conciliación
 ↓
F6  Cierre / auditoría
 ↓
F7  Operación / hardening / UAT / go-live
 ↓
PRODUCCIÓN FISCAL
```
