## 4. Pruebas de aceptación

### Objetivo

Convertir la implementación técnica en **evidencia objetiva de que el sistema puede operar fiscalmente sin introducir errores de cálculo, contaminación entre empresas, problemas de autorización, duplicidad de comprobantes o diferencias no explicadas frente al período de referencia**.

La aceptación no debe medirse por cobertura de código ni por cantidad de pruebas verdes. El criterio principal es que los **escenarios fiscales aprobados, los invariantes del dominio y los flujos operativos completos** produzcan resultados deterministas, auditables y reproducibles.

> **Regla de aceptación:** una prueba técnica puede estar verde y aun así el bloque permanecer bloqueado si el caso fiscal que valida todavía no está aprobado por el contador.

---

### 4.1 Escenarios dorados y propiedades del motor

#### Objetivo

Alcanzar **100 % de aprobación y ejecución satisfactoria de los escenarios dorados firmados**, complementándolos con pruebas de propiedades que verifiquen invariantes del motor tributario.

El documento de escenarios establece como gate F2 **30–50 casos resueltos a mano por el contador y 100 % verdes**. 

Los 17 escenarios actualmente identificados en `pendientes/PRIMERA_REV/dorados-propuestos-F0.json` **no deben considerarse todavía fixtures dorados**. Las fuentes señalan expresamente que están propuestos/no validados y que existen inconsistencias que deben resolverse antes de incorporarlos al runner. 

#### Proceso

1. Obtener la versión firmada de la matriz de reglas.
2. Resolver los 30–50 escenarios con el contador.
3. Normalizar:

   * porcentajes;
   * unidades monetarias;
   * bases;
   * fechas;
   * reglas aplicables;
   * precisión y redondeo.
4. Resolver específicamente inconsistencias como `ISLR-09`.
5. Convertir **únicamente los casos aprobados** a:
   `fixtures/tax-scenarios/*.json`.
6. Ejecutarlos automáticamente en CI.
7. Exigir:

   * `0` casos fallidos;
   * `0` casos omitidos;
   * `0` fixtures modificados para hacer pasar la prueba sin aprobación.
8. Registrar para cada resultado:

   * entrada;
   * `asOf`;
   * `ruleVersionId`;
   * snapshot de parámetros;
   * resultado esperado;
   * resultado obtenido;
   * explicación del cálculo.

#### Propiedades mínimas del motor

Las pruebas de propiedades deben verificar, como mínimo, los invariantes definidos para `tax-engine`:

* **Determinismo:** misma entrada + mismas reglas ⇒ mismo resultado.
* **Aislamiento temporal:** cambiar la fecha `asOf` puede cambiar la regla aplicable únicamente cuando existe una nueva vigencia.
* **Trazabilidad:** todo cálculo debe identificar la versión de regla utilizada.
* **No aleatoriedad:** el motor no debe depender de reloj, estado externo, red o aleatoriedad.
* **Conservación de precisión:** el resultado debe respetar las reglas de redondeo aprobadas.
* **Explicabilidad:** el resultado debe producir una explicación suficiente para reconstruir el cálculo.

La arquitectura ya establece el uso de Vitest para el motor y `fast-check` para las pruebas de propiedades. 

#### Evidencia requerida

```text
fixtures/tax-scenarios/
tests/tax-engine/
test-results/
  golden-results.json
  property-tests.json
```

Debe conservarse además la identificación de la versión de matriz/reglas contra la cual fueron ejecutadas las pruebas.

#### Criterio de aceptación

```text
Escenarios dorados firmados:       100 %
Escenarios ejecutados:             100 %
Fallos:                              0
Casos omitidos:                      0
Propiedades críticas:             100 % verdes
Reglas sin versión:                  0
Resultados no explicables:           0
```

**Bloqueador:** cualquier escenario fiscal firmado que falle bloquea la aceptación de F2 y, por extensión, el go-live fiscal.

### 4.2 Aislamiento entre empresas y autorización rol × empresa

#### Objetivo

Demostrar que un usuario autorizado para una empresa **no puede consultar, modificar, importar, emitir, cerrar ni descargar información perteneciente a otra empresa**, salvo que su matriz de autorización lo permita explícitamente.

La arquitectura define el aislamiento multitenant mediante **RBAC + empresa** y contempla una suite de fuga multitenant obligatoria en CI, junto con RLS. 

#### Matriz mínima de pruebas

Debe construirse una matriz:

| Usuario             | Empresa A | Empresa B | Acción                     | Resultado esperado   |
| ------------------- | --------: | --------: | -------------------------- | -------------------- |
| Administrativo      |         ✓ |         ✗ | importar                   | permitido / denegado |
| Administrativo      |         ✓ |         ✗ | consultar documentos       | permitido / denegado |
| Contador            |         ✓ |         ✓ | calcular                   | según autorización   |
| Contador            |         ✓ |         ✗ | emitir                     | denegado             |
| Auditor             |         ✓ |         ✗ | consultar                  | permitido            |
| Usuario sin empresa |         — |         — | cualquier operación fiscal | denegado             |

Los valores definitivos deben corresponder a la matriz de roles aprobada por el cliente; no debe asumirse que una propuesta de segregación todavía no aprobada constituye una decisión definitiva.

#### Casos obligatorios

Probar tanto:

**Acceso legítimo**

```text
usuario → empresa autorizada → recurso de empresa autorizada
                         → SUCCESS
```

como intentos de fuga:

```text
usuario A → ID documento empresa B
usuario A → ID período empresa B
usuario A → import_batch empresa B
usuario A → comprobante empresa B
usuario A → reporte empresa B
usuario A → descarga empresa B
```

Todos deben terminar en rechazo.

También deben probarse ataques mediante:

* manipulación de UUID;
* cambio de `company_id`;
* parámetros de URL;
* formularios;
* Server Actions;
* Route Handlers;
* descargas directas;
* consultas de reportes;
* operaciones administrativas.

**No basta con ocultar botones en la interfaz.** La autorización debe comprobarse en el servidor y en la base de datos.

#### Criterio de aceptación

```text
Fugas cross-company:       0
Acciones no autorizadas:   0
RLS bypass:                0
Descargas cruzadas:        0
Errores de autorización:   0
```

Una sola fuga de información entre empresas bloquea la aceptación.

### 4.3 Concurrencia de emisiones y numeración fiscal

#### Objetivo

Demostrar que entre **50 y 100 emisiones concurrentes** producen numeración consistente, sin duplicados ni huecos atribuibles al mecanismo de emisión.

La arquitectura define la reserva del número dentro de una transacción mediante actualización atómica de `document_series`, y establece explícitamente como garantía:

> **50–100 emisiones paralelas → 0 duplicados, 0 huecos.** 

#### Prueba

Crear una serie conocida:

```text
Inicial: 00000100
```

Lanzar simultáneamente, por ejemplo:

```text
100 solicitudes de emisión
```

y comprobar:

```text
00000101
00000102
00000103
...
00000200
```

sin:

* números repetidos;
* números asignados a dos comprobantes;
* números perdidos por carreras;
* números reutilizados;
* inconsistencias entre estado del comprobante y serie.

La prueba debe ejecutarse con concurrencia real contra PostgreSQL, no simplemente mediante un `for` secuencial.

#### También debe probarse el fallo transaccional

Simular:

```text
reservar número
       ↓
error durante emisión/renderizado/almacenamiento
       ↓
rollback
```

y verificar la política definida para el consumo del número.

La documentación arquitectónica establece que si falla cualquier paso de la transacción de emisión, **no se consume el número**; una vez emitido, el comprobante no se edita y una anulación conserva el número consumido. 

Debe existir una prueba específica para:

1. emisión exitosa;
2. emisión que falla antes de completar;
3. anulación posterior;
4. sustitución;
5. reintento;
6. dos solicitudes simultáneas sobre el mismo documento/evento.

#### Criterio de aceptación

```text
Emisiones concurrentes:       50–100
Duplicados:                    0
Huecos atribuibles al sistema: 0
Números reutilizados:          0
Comprobantes inconsistentes:   0
```

**Importante:** no confundir “sin huecos” con “sin números consumidos por anulaciones”. Una anulación fiscal conserva el número consumido y debe quedar trazada.

### 4.4 E2E por rol

#### Objetivo

Probar el sistema desde la perspectiva del usuario, no solamente mediante tests unitarios o de integración.

El flujo mínimo debe cubrir:

```text
Importar
   ↓
Validar
   ↓
Confirmar
   ↓
Calcular
   ↓
Emitir
   ↓
Generar comprobante
   ↓
Cerrar período
   ↓
Descargar
```

La suite definida en el proyecto contempla **Playwright E2E import → emitir → cerrar → descargar por rol**. 

#### Flujos

##### Administrativo

```text
login
  ↓
seleccionar empresa autorizada
  ↓
importar archivo
  ↓
visualizar staging
  ↓
corregir/rechazar errores
  ↓
confirmar importación
```

Debe comprobarse que no pueda ejecutar operaciones reservadas al contador.

##### Contador

```text
login
  ↓
seleccionar empresa
  ↓
validar documentos
  ↓
revisar cálculo
  ↓
emitir retención
  ↓
generar PDF/XLSX
  ↓
consultar trazabilidad
```

Cuando exista una decisión fiscal pendiente —por ejemplo G2— el E2E debe comprobar también el comportamiento **fail-closed**: el sistema debe bloquear la emisión cuando no existe criterio aprobado o existe ambigüedad.

La implementación G2 ya contempla bloqueo cuando existe ambigüedad, falta asignación o divergencia entre escenarios, antes de reservar numeración. 

##### Auditor

```text
login
  ↓
seleccionar empresa autorizada
  ↓
consultar período
  ↓
consultar documentos
  ↓
consultar comprobantes
  ↓
revisar eventos de auditoría
  ↓
descargar reportes
```

Debe comprobarse que las capacidades de modificación/emisión que no correspondan al rol sean rechazadas también desde el backend.

#### Criterio de aceptación

Cada rol debe tener:

```text
login                         ✓
empresa autorizada            ✓
operaciones permitidas       ✓
operaciones prohibidas       ✓
importación                   ✓
validación                    ✓
emisión                       ✓
cierre                        ✓
descarga                      ✓
auditoría                     ✓
```

No basta con que el flujo “principal” funcione: las acciones prohibidas forman parte de la prueba de aceptación.

### 4.5 Período completo: Excel vs. sistema

#### Objetivo

Ejecutar un **mes fiscal completo y real/anónimo**, procesándolo en paralelo:

```text
fuente original
      ├──→ Excel validado
      │
      └──→ ERP Tributario
```

y demostrar que ambos producen resultados equivalentes.

La arquitectura establece como criterio de calidad la comparación **celda a celda con el golden master**, mientras que el roadmap establece como métrica de aceptación:

> **M2 — “mes real = Excel”**

y exige reconciliación del período. 

#### El período debe contener, cuando corresponda

* compras;
* ventas;
* documentos gravados;
* documentos exentos;
* notas de crédito;
* notas de débito;
* retenciones;
* pagos/abonos;
* sucursales;
* máquinas fiscales/Z;
* diferencias cambiarias, si aplican;
* documentos del período registrados posteriormente.

No debe construirse artificialmente un mes perfecto si el objetivo es demostrar comportamiento operativo real.

#### Comparación

La comparación debe realizarse en varios niveles.

**Nivel 1 — Documentos**

```text
cantidad
identificadores
fechas
bases
IVA
retenciones
moneda
```

**Nivel 2 — Libros**

```text
compras Excel      = compras ERP
ventas Excel       = ventas ERP
```

**Nivel 3 — Resumen IVA**

```text
base gravada
IVA débito
IVA crédito
retenciones
totales
```

**Nivel 4 — Comprobantes**

```text
cantidad
numeración
base
porcentaje
monto retenido
empresa
beneficiario
período
```

**Nivel 5 — Reportes**

```text
Excel final
PDF
CSV
```

#### Política de diferencias

El resultado esperado es:

```text
Diferencias = 0
```

Cuando exista una diferencia, debe clasificarse obligatoriamente:

| Tipo                                 | Tratamiento               |
| ------------------------------------ | ------------------------- |
| Error de datos                       | corregir                  |
| Error de cálculo                     | bloquear                  |
| Error de importación                 | corregir                  |
| Diferencia por redondeo              | justificar y aprobar      |
| Diferencia por interpretación fiscal | bloquear hasta decisión   |
| Diferencia de formato                | documentar                |
| Diferencia de versión normativa      | documentar regla/vigencia |
| Diferencia legítima del sistema      | documentar y aprobar      |

**“Documentada” no significa automáticamente “aceptada”.**

Toda diferencia que afecte:

* base imponible;
* IVA;
* retención;
* período;
* numeración;
* total fiscal;

requiere revisión y aprobación antes de considerar satisfactorio el período.

## 4.7 Gate de aceptación

La fase puede considerarse **ACEPTADA** solamente cuando se cumpla simultáneamente:

| Criterio                               |           Umbral |
| -------------------------------------- | ---------------: |
| Escenarios dorados firmados ejecutados |        **100 %** |
| Escenarios dorados fallidos            |            **0** |
| Property tests críticos                | **100 % verdes** |
| Fugas entre empresas                   |            **0** |
| Operaciones no autorizadas exitosas    |            **0** |
| Emisiones concurrentes                 |       **50–100** |
| Duplicados de numeración               |            **0** |
| Huecos atribuibles al sistema          |            **0** |
| Flujos E2E críticos                    |        **100 %** |
| Período completo conciliado            |        **100 %** |
| Diferencias fiscales no aprobadas      |            **0** |
| Evidencia reproducible                 |        **100 %** |

### Regla de bloqueo

Cualquiera de los siguientes mantiene el sistema **NO APTO PARA PRODUCCIÓN**:

* escenario dorado firmado fallido;
* regla fiscal utilizada sin versión aprobada;
* fuga cross-company;
* autorización rol×empresa incorrecta;
* duplicación de numeración;
* hueco de numeración no explicado;
* emisión de una retención con información fiscal ambigua;
* E2E crítico fallido;
* diferencia fiscal no explicada entre Excel y sistema;
* diferencia explicada pero todavía no aprobada;
* período cerrado que pueda modificarse silenciosamente.

### Resultado esperado de Fase 4

Al finalizar esta fase debe poder afirmarse, con evidencia:

> **El sistema reproduce los escenarios fiscales aprobados, mantiene aislamiento y autorización por empresa, soporta emisiones concurrentes sin corrupción de numeración, completa los flujos operativos por rol y reproduce un período fiscal completo sin diferencias no explicadas frente al sistema de referencia.**

Esto constituye el **gate de aceptación funcional, fiscal, de seguridad y de integridad transaccional** previo al paso a pruebas piloto/producción.
